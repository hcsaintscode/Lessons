Build an App with Lovable

Specify, build, iterate, and ship a real web app — from an IOSP spec to a deployed URL

At a Glance

Driving Question
Can you specify a real problem precisely enough that an AI builds the app you intended — and then iterate it to something people actually use?
Big Idea
Prompt-writing is specification. The IOSP model you learned becomes a precise spec; an AI builder turns it into a deployed app; and your judgment — testing, iterating, evaluating what the AI got right and wrong — is what makes it good.
Format
Project — ~4–5 sessions (phase tabs). Individual or pairs, each driving lovable directly.
Deliverable
A deployed, shareable app + a completed Project Guide + a build reflection comparing spec vs. output + a showcase

Learning Objectives

Students will be able to:

  • Apply DPTR to define and scope a real problem with clear success criteria
  • Translate an app design into a precise IOSP specification
  • Use precise natural-language prompts to build and iterate an app with an AI builder, spending limited credits strategically
  • Critically evaluate AI-generated output (what matched the spec, what didn't, what to change) and ship a working, shared app

Setup — Before You Start

Accounts, credit budget, and prompting = specification

"In Week 2 you built an input→process→output app by hand in real JavaScript. lovable.dev is that same IOSP idea at full scale — but instead of typing the code, you SPECIFY the app in precise language and an AI writes real React code for you. Your leverage is the quality of your specification and your judgment about what it produces."

What Is lovable.dev?

  • AI APP BUILDER — lovable.dev is an AI app builder: you describe the app you want and it generates a working full-stack web app for you.
  • REAL CODE UNDERNEATH — it writes real React/TypeScript under the hood and deploys it to a public URL. It's not a mockup — it's the same kind of code you glimpsed in StackBlitz, just AI-generated and at app scale.
  • SMALL LOOPS — you refine the app by prompting in small, targeted loops: read what it built, test it, then ask for one precise change at a time.

The free plan gives about 5 build credits per day — they don't roll over, so you get roughly 30 a month. Every prompt you send the AI costs a credit. Plan the full spec on paper FIRST: one precise prompt beats many vague ones. Vague prompting is how you burn a day's credits with nothing to show.

Run this individually or in pairs, each driving lovable directly. Pairs stretch credits and enable pair-spec review. Before anyone spends a credit, require a "spec review": a peer checks that the spec is complete — all four IOSP parts (Inputs, Outputs, Storage, Processing) present and specific enough to build from.

Define & Spec

DPTR + a precise IOSP spec — all on paper, no credits spent

"No credits spent yet. A precise spec is the whole game. Everything you get right here saves you credits and rework later — and everything you leave vague, the AI will guess at."

Define (DPTR)

"Pick a real problem with genuine stakes — in your own life, a team or club you're in, a job you have, or your community. In your Project Guide, write a clear problem statement, name a specific target user (who exactly has this problem?), and define success criteria: how will you know the app actually works?"

Push students to name a specific user, not "everyone." "Students on my robotics team who forget which parts we've ordered" is a spec you can build for. "People who are busy" is not. The tighter the audience, the tighter the app.

Specify (IOSP → spec)

"Now translate your design into a precise IOSP spec. This is engineering, not a wish list — name the data, the controls, and the exact logic, specifically enough that a builder could act on it without guessing."

  • INPUTS — the fields and controls, with their types (text, number, date, dropdown, checkbox, button).
  • OUTPUTS — exactly what gets rendered on screen (a list, a total, a message, a chart).
  • STORAGE — what data persists between visits, and in what shape.
  • PROCESSING — the logic: which of the four kinds (if/then, comparing, finding a match, counting) plus any rules that combine them.

Draft the Build Prompt

"Your IOSP spec becomes a structured first prompt. Write it in order — Inputs, Outputs, Storage, Processing — plus a note on the audience and vibe. Treat this like a spec you're handing an engineer: precise language, no ambiguity."

"Here's a strong example for a study-session planner: Build a study-session planner web app. INPUTS: a form to add a subject, a due date, and estimated hours. OUTPUTS: a prioritized list of sessions sorted by due date, and total hours this week. STORAGE: persist the sessions. PROCESSING: sort by due date (comparing), flag anything due within 2 days (if/then), and sum weekly hours (counting). Clean, minimal UI suitable for a high-school student. Use simple local persistence."

A good spec names the data, the controls, the logic, and the audience/vibe. Vague specs waste credits and force the AI to guess; precise specs build right the first time.

  • What's the ONE core feature that must work for this to solve the problem?
  • What data does the app need to remember between visits?
  • Which of the four kinds of processing does your logic use?

Each student/pair has a scoped problem, a complete IOSP spec, and a peer-reviewed first build prompt — before opening lovable.

Build & Iterate

Direct the AI; evaluate its output critically; iterate in small loops

"Paste your first prompt, then evaluate critically and iterate in small, specific loops. You are the engineer directing the AI, not a spectator — the AI produces, you judge and steer."

Facilitating the Build

  • Have students READ and TEST what was built before prompting again
  • Make one targeted change per prompt — not a list of five things
  • When the AI's output diverges from the spec, name the gap precisely in the next prompt
  • Use lovable's Fix option when the app throws an error
  • Keep a build log: prompt → result → credits spent

Evaluating AI Output (teach this)

  • MATCH THE SPEC? — Does what it built actually match what you specified?
  • ADDED / MISSED — What did the AI add that you didn't ask for, and what did it miss?
  • LOGIC CORRECT? — Is the processing logic actually right? Test it with real inputs — try edge cases, not just the happy path.
  • VERIFY, DON'T TRUST — Don't accept output uncritically. Confirm the behavior yourself before you call it done.

Out of credits for the day? Switch to planning the next iteration precisely on paper so tomorrow's credits land instantly. Track credits in the build log so no one is surprised. Running out is a planning day, not a failure.

Publish

"When your app works, use lovable's Publish button to deploy it to a shareable URL. Paste that link into your Project Guide — that's your real, deployed app on the internet."

Ship & Reflect

User-test with real people, showcase, and reflect on spec vs. output

"You shipped something real. Now put it in front of the people who actually have the problem, defend your design choices, and reflect on the gap between what you specified and what the AI produced."

User Testing (Extend Beyond the Classroom)

"Share your deployed link with REAL target users — the actual people who have this problem, whether that's your teammates, family, coworkers, or community. Collect specific feedback, then make at least one improvement based on it (credits permitting), or document exactly the change you'd make."

Showcase / Defend

"Each student or pair demos the app, states the problem and the IOSP spec behind it, and answers one question about a design or logic decision — why did you build it that way?"

  • Keep demos tight — the app, the problem, the spec, one defended decision
  • Ask each presenter to point to their app's inputs, processing, storage, and outputs in the running app
  • Have the audience surface one thing they'd extend or challenge

Build Reflection (the key HS deliverable)

  • What did you specify vs. what did the AI actually produce?
  • Where did it diverge from your spec, and how did you correct it?
  • What did precise specification get you that a vague prompt wouldn't have?
  • Why does this problem matter to you?
  • What would you build next, or how would you extend this app?

"In one sentence: what problem does your app solve, who is it for, and what's the one thing the AI got wrong that you had to fix?"

Additional Notes for the Teacher

Managing the Free Tier

  • About 5 build credits per day, no rollover, roughly 30 per month
  • Spec fully on paper first — every prompt costs a credit
  • Precise prompts beat many vague ones
  • Pairs stretch credits and enable spec review
  • A no-credit day is a spec/iteration-planning day, not a lost day

Connecting to Week 2 (StackBlitz → Lovable)

  • Week 2's hand-coded input→process→output shows what's happening under the hood
  • lovable is the same IOSP model — AI-generated and at full app scale
  • Students should be able to point to their app's inputs, processing, storage, and outputs in the running app

Good Project Scopes

  • Trackers and planners; quiz/flashcard tools
  • Sign-up or directory pages; decision helpers; simple dashboards
  • One core feature done well
  • Avoid payments, third-party OAuth, or large datasets on the free tier

Evaluating AI Output

  • Teach students to verify behavior with real test inputs — not to trust that generated code is correct
  • Correctness of the processing logic is graded
  • Model this: run an edge case live and show the AI got it subtly wrong

Differentiation

  • Support: Provide a spec template plus a strong example prompt to adapt rather than start from scratch
  • Advanced: Add a second feature, use multiple processing types, run a real user-feedback iteration, or critique the AI's generated structure/UX

Safety & Ethics

  • No real personal data in apps — use made-up test data
  • Review the app before sharing it widely
  • Be mindful of what the app collects if others use it

If You're Running Behind

  • Define & Spec is the priority — the spec is most of the learning
  • A single strong prompt + publish is a valid minimum
  • User testing and reflection can be assigned as homework
