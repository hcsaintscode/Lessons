What Is a Computer?

Week 2 — The IOSP model, and building a real app prototype in JavaScript

At a Glance

Driving Question
How does the Input–Output–Storage–Processing model let us design AND build an app that solves a problem?
Big Idea
Every computer is Input, Processing, Storage, Output. Once you can model a problem as IOSP, you can turn that model directly into working code.
Schedule
Day 1 Learn (45) · Day 2 Explore (90) · Day 3 Create (90)
Week Deliverable
A working HTML/JS app prototype (input → process → output) + IOSP design doc, presented to the class

Learning Objectives

Students will be able to:

  • Define IOSP and analyze real computing systems in those terms
  • Explain the four kinds of processing (If/Then, Comparing, Finding a Match, Counting) and identify them in code
  • Map an app's IOSP design directly to HTML inputs, JavaScript processing, and rendered output
  • Build, test, and present a working app prototype

Day 1 — Learn: What Is a Computer? The IOSP Model

A system model you can turn into code

Time Activity
0–6 min Hook — what makes a computer general-purpose?
6–20 min Mini-lesson — IOSP as a system model + the two Code.org videos
20–32 min Four kinds of processing (with tiny code examples)
32–42 min IOSP analysis of a real app (whole class)
42–45 min Exit ticket

Hook (0–6 min)

"A calculator does math. A typewriter types. But your laptop can be a calculator, a typewriter, a synthesizer, and a game — all at once. What makes a computer able to do ANY of these? Hold that thought."

The answer: it's programmable, and every program is built from the same primitive: take Input, do Processing (using Storage), produce Output. IOSP is the universal shape of computation.

Mini-lesson: IOSP as a System Model (6–20 min)

"A computer isn't defined by having a screen or a keyboard. It's a programmable machine that processes information. Whatever the program, the shape is the same: data flows in, gets transformed, may be remembered, and results come out. That shape is IOSP."

  • COMPUTER — a programmable machine that processes information.
  • INPUT — the data that flows in (from users, sensors, files, or other programs).
  • PROCESSING — the transformation that turns input into output; this is where the problem actually gets solved.
  • STORAGE — information the system remembers to use later.
  • OUTPUT — the results that come out (to a screen, a file, a speaker, or another program).

Frame IOSP as a SYSTEM MODEL, not just vocabulary: data flows in (input), is transformed (processing), may be remembered (storage), and results come out (output). This is the mental picture students will map directly onto HTML and JavaScript on Day 2.

Show the two Code.org videos:

  • How Computers Work: Hardware & Software
  • How Computers Work: What Makes a Computer, a Computer?

Four Kinds of Processing (20–32 min)

All processing is built from a small set of moves. Here are four, each with a tiny piece of plain JavaScript.

If/Then — do something only when a condition is trueif (age >= 13) { showContent(); }
Comparing — check which value is bigger / smaller / equalif (score > highScore) { highScore = score; }
Finding a Match — search a list for an itemcontacts.find(c => c.name === "Mom")
Counting — keep a running totalcount = count + 1;

"Every bit of processing you'll ever write is built from simple moves like these four."

IOSP Analysis of a Real App (32–42 min)

"Let's model a real app as IOSP together — take a ride-share app. What's the Input? (pickup, destination, tap). Processing? (match you to a nearby driver — that's Finding a Match; calculate price — comparing/counting). Storage? (your trip history, saved places). Output? (map, ETA, price)."

Emphasize that Processing is where the problem actually gets solved — input and output are just the edges.

"Model any app you use as IOSP. Name a specific Input, Processing step (which of the 4 kinds?), Storage item, and Output."

Every student can model a real app as IOSP and name which kind of processing it uses.

Day 2 — Explore: From IOSP Model to Code + Launch the Build

Seeing how IOSP becomes HTML and JavaScript — then starting your own

Time Activity
0–5 min Review IOSP
5–35 min Guided demo — walk through a working example app and map each part to IOSP
35–45 min Define the problem for YOUR app (partner)
45–70 min Design the IOSP + plan the code (what inputs, what processing, what output)
70–90 min Start building in StackBlitz

Review IOSP (0–5 min)

"Quick recall: what are the four parts of IOSP? And what are the four kinds of processing — If/Then, Comparing, Finding a Match, Counting?"

Guided Demo: IOSP Becomes Code (5–35 min)

"I'm going to show you a tiny finished app, and we'll label every part with IOSP. This is the pattern your app will follow."

The reference app is a simple Study Break Picker: the user picks how much time they have and their energy level (INPUT via dropdowns), clicks a button, and the app suggests an activity (OUTPUT) using if/then logic (PROCESSING). It is fully offline — no API, no internet needed.

index.html<!DOCTYPE html> <html> <head><meta charset="UTF-8"><title>Study Break Picker</title></head> <body> <h1>Study Break Picker</h1> <label>Time I have: <select id="time"> <option value="5">5 minutes</option> <option value="15">15 minutes</option> <option value="30">30 minutes</option> </select> </label> <label>My energy: <select id="energy"> <option value="low">Low</option> <option value="high">High</option> </select> </label> <button id="go">Suggest a break</button> <p id="result"></p> <script src="index.js"></script> </body> </html>
index.js// INPUT: read the dropdowns when the button is clicked document.getElementById("go").addEventListener("click", function () { const time = Number(document.getElementById("time").value); const energy = document.getElementById("energy").value; // PROCESSING: if/then + comparing decide the suggestion let suggestion; if (energy === "high" && time >= 30) { suggestion = "Go for a walk outside."; } else if (energy === "high") { suggestion = "Do 20 jumping jacks."; } else if (time >= 15) { suggestion = "Close your eyes and rest."; } else { suggestion = "Drink some water and stretch."; } // OUTPUT: show the result on the page document.getElementById("result").textContent = suggestion; });

Map it to IOSP: INPUT = the two <select> dropdowns; PROCESSING = the if/then + comparing in JS; OUTPUT = writing to the <p id="result">; STORAGE = this simple version stores nothing — a stretch goal is to save the last suggestion with localStorage.

For the non-CS teacher: "You do NOT need to write this from scratch or memorize it. Open the reference app in StackBlitz, run it, and change ONE thing (add an option, change a suggestion). Seeing it work is the goal." The self-study module has the same code embedded so students can experiment.

Define the Problem (35–45 min)

"With your partner, define a real problem your app will solve. Same criteria as always: real, well-defined, and an information problem a computer can help with."

Design the IOSP + Plan the Code (45–70 min)

"Before coding, write your app's IOSP on the worksheet, and note: what HTML inputs (dropdowns, text boxes, buttons)? what processing (which of the four kinds)? what output (text, a list, a number)? This plan IS your code outline."

Start Building in StackBlitz (70–90 min)

"Open StackBlitz, start from the Study Break Picker as a template, and begin changing it into YOUR app. Keep it small — one input area, one button, one output."

Scope creep is the #1 risk. Keep prototypes to: a few inputs, one processing step, one output. A working tiny app beats a broken ambitious one.

Every pair has defined a problem, written their app's IOSP, and has the reference app running in StackBlitz.

Day 3 — Create: Build, Test, Present

Finishing and demoing a working prototype

Time Activity
0–5 min Recap
5–45 min Build & test the prototype
45–60 min Peer testing (swap and try each other's apps)
60–75 min Revise based on feedback
75–90 min Demos + IOSP explanation

Recap (0–5 min)

"Today you finish a WORKING prototype, test it, and demo it."

Build & Test the Prototype (5–45 min)

"Get your app working end to end: input goes in, processing runs when the button is clicked, output appears. It doesn't need to be fancy — it needs to WORK."

Facilitation (non-CS teacher survival tips):

  • If the app "does nothing" on click: check the button id matches the getElementById, and that index.js is linked
  • If nothing shows: check the output element id matches
  • Encourage console.log to see values; StackBlitz shows errors in its preview/console
  • Direct deep code questions to pairs helping pairs; you facilitate, you don't debug alone

Peer Testing (45–60 min)

"Swap computers with another pair. Try to use their app. Report: did it work? was the output clear? one suggestion."

Revise (60–75 min)

"Fix what peer testing found. Optionally add a stretch goal: remember the last result with localStorage (Storage!)."

Demos + IOSP Explanation (75–90 min)

"Each pair demos their working app and explains its IOSP: what's the input, what processing (which of the four kinds), what output, and what (if anything) it stores."

The Study Break Picker code shown on Day 2 is the canonical working example. If a pair gets stuck, have them start from it and change one thing at a time — it is guaranteed to run in StackBlitz with no setup.

localStorage stretch goal (Storage)

Save the last suggestion after building it, and show it again when the page loads:

save it (add after the OUTPUT line)localStorage.setItem('lastBreak', suggestion);
restore it (run once when the page loads)document.getElementById('result').textContent = localStorage.getItem('lastBreak') || '';

Every pair demoed a working prototype and explained its IOSP.

Additional Notes for the Teacher

Differentiation

  • Support: Let them modify the reference app minimally (change suggestions/options) rather than build new; pair a nervous coder with a confident one
  • Challenge: Add more inputs; use an array + Finding a Match instead of if/then; implement the localStorage storage stretch goal; add input validation

For the Non-Technical Teacher

  • You are NOT expected to debug JavaScript live. Your job: keep pairs unblocked, enforce small scope, and make sure everyone can run the reference app. The self-study module embeds the same code for students to experiment independently.

Materials Needed

  • Computers with a browser + StackBlitz (no installs), the student worksheet, projector for the demo

Connecting to the Semester Arc

  • This is the bridge INTO the Programming phase. Students just turned an IOSP model into running code — exactly what all of programming is.

If you're running behind

  • Everyone modifying the reference app (vs. building from scratch) is a fine floor; a working modified app meets the objective
  • Peer testing can shrink to 10 min; protect the demos
