Input & Decisions: Apps That Respond to You

Week 3 — Read what the user types or picks, then make the app decide

At a Glance

Driving Question
How does an app react differently depending on what the user types or chooses?
Big Idea
Apps read input (text, dropdowns), combine strings, and use IF statements to decide what to do. Different input → different output. That's the app making decisions.
Schedule
Day 1 Learn (45 min) · Day 2 Explore (90 min) · Day 3 Create (90 min)
Week Deliverable
An app that takes input and uses conditionals to produce different outputs — shared via link

Learning Objectives

Students will be able to:

  • Read user input from a text box and a dropdown (getText / getProperty)
  • Combine strings to build a personalized message
  • Write if / if-else statements using comparison operators to make decisions
  • Explain how different input leads to different output

Day 1 — Learn: Reading Input & Building Strings (Mad Lib)

Get what the user types, then talk back

Time Activity
0–8 min Hook — "The apps you love react to YOU"
8–24 min Mini-lesson — input elements; getText; strings + joining with +
24–38 min Build a mini Mad Lib together in App Lab
38–42 min App Lab lesson pointer (Code.org Lessons 6–9)
42–45 min Exit ticket

Hook (8 min)

"The apps you love feel personal because they react to YOU — your name, your choices. Today your app reads what someone types and talks back to them by name."

Ask for a few examples out loud: a game that greets you by name, a quiz that gives you a result, a playlist that fits your mood. All of them do the same thing under the hood — they read something from you (input) and respond to it. Keep that word, input, on the board.

Mini-lesson: Reading Input & Joining Text (16 min)

"Last week our apps could remember a number. This week they start listening. First we read what the user types, then we build a message back to them by gluing pieces of text together. Here are the four words you need."

  • INPUT ELEMENT — a text box or dropdown the user fills in (the app reads what they put there).
  • getText — reads what's currently in a text box: getText("nameInput")
  • STRING — text data, always written inside quotes: "Hello"
  • CONCATENATION — joining strings together with + to build a bigger message.

"Think of strings like beads on a string. Each piece of text is a bead — the word Hello, a comma, the name someone typed — and the plus sign snaps them together into one message. Read the input, snap it into a sentence, show it on screen."

var name = getText("nameInput"); setText("output", "Hello, " + name + "! Welcome.");

Strings are just text in quotes; the + glues them together. The Mad Lib is the classic, fun first use — read several inputs (a name, an animal, a silly verb) and drop them into a goofy sentence. When it reads back what a student typed, the whole idea clicks instantly.

Build a Mini Mad Lib — Together (14 min)

"Everyone open App Lab. In Design Mode, drag on two text inputs (rename their ids to nameInput and animalInput), a button, and a label called output. Now switch to Code — we'll read both inputs and build one silly sentence."

onEvent("goButton", "click", function() { var name = getText("nameInput"); var animal = getText("animalInput"); setText("output", name + " rode a giant " + animal + " to school!"); });

The whole magic is that name and animal hold whatever the user typed. Type different words, press the button, and the sentence changes. That's input driving output.

App Lab Lesson Pointer (4 min)

These skills line up with Code.org's csp5-virtual Unit 1, Lessons 6–9 (If-Statements; User Input & Strings / Mad Lib; Boolean Expressions & Dropdowns; if-else-if). Point students there for extra guided practice.

studio.code.org/courses/csp5-virtual/units/1

What does getText do? What does the + do when used with strings?

Every student read a text input and displayed a personalized string.

Day 2 — Explore: Making Decisions (If-Statements & Dropdowns)

Different input, different output

Time Activity
0–5 min Review — getText + joining strings
5–25 min If-statements — running code only when a condition is true
25–50 min Comparison operators + if-else + dropdowns
50–75 min Build a decider (dropdown → if-else → different output)
75–90 min Record vocab + checkpoint

Review (5 min)

"Quick recall from yesterday: how do we read what someone typed? (getText.) And how do we build a message from pieces of text? (Join them with the plus sign.) Today we take that input and let the app DECIDE what to do with it."

If-Statements: Deciding When to Act (20 min)

"An IF statement is how an app makes a decision. It runs a chunk of code only WHEN a condition is true. If the condition is false, that code is skipped. That's it — a question, and code that only runs when the answer is yes."

if (age >= 13) { setText("msg", "You can sign up."); }

Read it out loud as a sentence: "IF age is greater than or equal to 13, then show the sign-up message." Everything inside the curly braces only happens when the answer to the question is yes.

Comparison Operators, If-Else & Dropdowns (25 min)

"To ask a question in code we use comparison operators: == means 'is equal to,' > means 'greater than,' < means 'less than.' And if-else lets us do one thing when the answer is yes and something ELSE when it's no."

"A dropdown is a perfect input for this — the user picks one option, we read it with getText, and the if-else decides what to show. Let's read a mood dropdown and give different advice for different moods."

var mood = getText("moodDropdown"); if (mood == "happy") { setText("advice", "Go share it with a friend!"); } else { setText("advice", "Take a short walk. 🙂"); }

To compare for equality inside a condition, use == (double equals). A single = is assignment (that's how we put a value in a box last week). Mixing them up is a classic beginner bug — == asks a question, = stores a value.

Build a Decider (25 min)

"Now your turn. Wire up a dropdown (or a text input) to an if-else so that different choices show different output. Start with just two outcomes — the 'if' and the 'else.'"

  • Require at least one working if-else that is driven by an input.
  • Watch for = vs == confusion — the single most common conditional bug.
  • Watch for reading the wrong element id (the condition compares against a value that never appears).
  • Encourage a third branch with else if as a stretch for students who finish early.

== (compare) vs = (assign) is the #1 conditional bug for beginners. If a condition is behaving strangely — or App Lab flags an error — check for a single equals inside the parentheses first.

Record Vocab (part of 75–90 min)

Have students log this week's words in their notebooks or worksheet: input, getText, string, concatenation, if, if-else, and comparison operator (==, >, <).

Every student has an app where a dropdown or input drives an if-else that changes the output.

Day 3 — Create: Build a Decision App

An app that decides — make it yours

Time Activity
0–5 min Launch — "Build a decision app that's YOURS"
5–20 min Plan — input, outputs, and the rule
20–70 min Build in App Lab
70–82 min Share & test with a partner
82–90 min Reflection

Launch (5 min)

"Build a decision app that's YOURS — a personality quiz, a 'what should I eat/watch/wear' recommender, a mood-advice app, a study-or-break picker. It reads input and shows different output depending on the answer."

Make It Yours: Plan Your Decision App (15 min)

Before touching code, have each student answer three questions on paper. This is where they make real decisions about what they're building.

  • What input does it take — a dropdown or a text box? What are the choices?
  • What are the possible outputs — the different messages or results it can show?
  • What's the rule — if this input, then show that output? Write one line for each branch.

Push students to pick a topic they actually care about — their sport, their favorite shows, what to do when they're bored, a decision they really face. The more personal the topic, the more they'll want to make it work.

Build (50 min)

"App Lab time. Get your input on the screen, then write the if-else that reacts to it. Test as you go — don't wait until the end."

  • Start with 2 outcomes (a plain if-else), then add more with else if.
  • Test each branch — pick every option and confirm the output changes correctly.
  • Use == for comparisons inside the condition.
  • Check element IDs — the id in getText must match the id in Design Mode exactly.

Extend Beyond the Classroom: Share & Test (12 min)

"Share your App Lab link. Trade with a partner and have them try EVERY option to make sure each one works. Then take it home — share it with a friend or someone in your family and see if the advice actually fits them."

  • Use App Lab's Share button to get a keepable link — this is a real app students can hold onto.
  • Partner testing catches branches that were never checked.
  • Encourage students to try it out at home with family or friends and bring back what they said.

Reflection (8 min)

  • What does your app decide, and why did you pick this idea?
  • Where's the input, the decision (processing), and the output in your app?
  • What's one more branch you'd add if you kept building it?
  • Where in your own life could an app that decides based on input actually be useful?

Additional Notes

Differentiation

  • Support — hand out a starter with the input and one branch already wired, so the student just adds the else; or a fill-in-the-blank condition with the comparison left as a gap.
  • Advanced — add else if branches, combine two conditions in one if, or validate empty input before deciding.

For the Non-Technical Teacher

  • The one bug to know: == compares, = assigns. Inside an if condition you almost always want ==.
  • If a decision always does the same thing, check that the condition uses == and that getText reads the right element id.

Connecting the Arc

  • Conditionals are the "smart" part of Processing in IOSP — the app choosing what to do based on input.
  • This is also what you'll describe to an AI builder ("when the user picks X, show Y") and what you'll debug when it chooses wrong.
