Input & Decisions: Apps That Respond to You

Week 3 — Booleans, comparisons, and conditional logic in code

At a Glance

Driving Question
How does code choose between many possible responses to the user?
Big Idea
Programs decide with Boolean expressions (true/false) and conditionals. if / if-else / if-else-if chains pick a path; compound conditions (&&, ||, !) combine tests. This is the logic engine of Processing in IOSP.
Schedule
Day 1 Learn (45) · Day 2 Explore (90) · Day 3 Create (90)
Week Deliverable
A code-mode app that reads input and uses conditional logic (incl. an if-else-if or a compound condition) to produce different outputs — shared via link

Learning Objectives

Students will be able to:

  • Read user input (text + dropdown) and manipulate strings in code
  • Write Boolean expressions with comparison operators (==, !=, >, <, >=, <=)
  • Build if / if-else / if-else-if chains that select among multiple outcomes
  • Combine conditions with compound Boolean operators (&&, ||, !)

Day 1 — Learn: Input, Strings & Boolean Expressions

Reading input and expressing true/false

Time Activity
0–7 min Hook — from remembering to deciding
7–24 min Mini-lesson — getText; strings; Boolean expressions + comparison operators
24–38 min Write conditions in code driven by input
38–42 min App Lab lesson pointer (Code.org Lessons 6–9)
42–45 min Exit ticket

Hook (7 min)

"Last week your app remembered values. Today it makes CHOICES. Every choice a program makes comes down to a true/false question — a Boolean expression — and code that branches on the answer."

Draw the split on the board: a single arrow of code hits a diamond and forks two ways. Ask students where they've seen an app respond differently to different input — a login that accepts or rejects, a quiz that scores, a form that warns "password too short." Every one of those is a Boolean question answered in code.

Mini-lesson: Input, Strings & Boolean Expressions (17 min)

"To decide, an app needs something to decide about. That's INPUT. You read it, sometimes reshape it as a STRING, then ask a true/false question about it — a Boolean expression — using comparison operators."

  • INPUT — read what the user typed or picked: getText("nameInput") from a text box, or the current value of a dropdown.
  • STRING — text data. Join text with concatenation: "Hi, " + name builds a new string.
  • BOOLEAN EXPRESSION — an expression that evaluates to exactly true or false. That's the question the code branches on.
  • COMPARISON OPERATORS — build Boolean expressions: == (equal), != (not equal), >, <, >=, <=.

"Burn this in now: == asks a question — 'are these equal?' — and returns true or false. = is a command — 'store this value.' One compares, one assigns. Mixing them up is the single most common bug you'll write all year."

// INPUT: read a number the user typed var age = getNumber("ageInput"); // BOOLEAN EXPRESSION with a comparison operator drives the branch if (age >= 13) { setText("msg", "You can sign up."); }
// a STRING comparison in a condition var code = getText("codeInput"); if (code == "OPEN2027") { setText("msg", "Access granted."); }

Connect to IOSP: the condition is the PROCESSING step. Input flows in, a Boolean expression tests it, and the branch you take decides the Output. Conditionals are the decision logic at the heart of Processing.

Day 2 — Explore: if-else-if Chains & Compound Conditions

Choosing among many outcomes; combining tests

Time Activity
0–5 min Review — Boolean expressions + comparison operators
5–25 min if-else-if chains — choosing among multiple branches
25–50 min Compound conditions — &&, ||, !
50–75 min Build a small quiz/recommender with scoring
75–90 min Record vocab + checkpoint

Review (5 min)

"Quick recall: a Boolean expression evaluates to true or false. Name the comparison operators — ==, !=, >, <, >=, <=. Yesterday one question, one branch. Today: many outcomes, and questions that combine."

if-else-if Chains (20 min)

"When there are more than two possible outcomes, chain the tests. An if-else-if chain checks each condition in order and runs the FIRST one that's true — then it stops. Every branch after that is skipped."

var score = getNumber("scoreInput"); if (score >= 90) { setText("grade", "A"); } else if (score >= 80) { setText("grade", "B"); } else if (score >= 70) { setText("grade", "C"); } else { setText("grade", "Keep going"); }

Only the FIRST true branch runs. Have students trace score = 95 out loud: it's >= 90, so it prints "A" and skips the rest — even though 95 >= 80 is also true. That "stop at the first true" rule is exactly why branch ORDER matters.

Compound Conditions: &&, ||, ! (25 min)

"Sometimes one test isn't enough — you need two things to be true at once, or either of two things, or the opposite of something. That's what the compound operators are for: && (and), || (or), ! (not)."

var score = getNumber("scoreInput"); var streak = getNumber("streakInput"); // BOTH must be true if (score >= 90 && streak >= 3) { setText("badge", "On fire!"); } // EITHER one being true is enough if (score >= 100 || streak >= 5) { setText("badge", "Bonus unlocked"); } // NOT flips a Boolean if (!(score >= 60)) { setText("badge", "Below passing"); }

&& needs BOTH sides true; || needs EITHER side true; ! flips true to false. Order and grouping matter — use parentheses to make the grouping obvious, e.g. (a && b) || c.

Build a Quiz / Recommender (25 min)

"Now put it together. Build a small app: read a few inputs, use an if-else-if chain — with at least one compound condition — to produce a result. Optionally keep a score variable that adds up as the user answers (that ties straight back to Week 2 state)."

  • Require an if-else-if chain PLUS at least one compound condition (&&, ||, or !).
  • Test EVERY branch — feed inputs that should land in each outcome, including the final else.
  • Watch for = vs ==, the wrong comparison operator, and "unreachable" branches (a broad condition earlier catching everything).
  • If they keep a score, console.log(score) after each update to confirm it's changing as expected.

A broad condition placed FIRST can make later branches unreachable — if score >= 70 comes before score >= 90, the "A" branch never runs. And == vs = is still the classic bug. When a branch misbehaves, console.log the values you're comparing so you can see what the condition actually saw.

Record Vocabulary (part of 75–90)

  • Boolean expression — evaluates to true or false.
  • Comparison operator — ==, !=, >, <, >=, <=.
  • if-else-if — a chain that runs the first true branch and stops.
  • Compound condition — combines tests with &&, ||, !.

Every student has an app with an if-else-if chain AND at least one compound condition, with all branches tested — including the final else.

Day 3 — Create: Build a Decision App

A quiz/recommender of your choice — make it yours

Time Activity
0–5 min Launch — pick your decision app
5–20 min Spec the logic — inputs, rules, where a compound condition is needed
20–70 min Build in code mode
70–82 min Peer test — swap links, hunt for wrong/unreachable results
82–90 min Reflection + AI-bridge

Launch (5 min)

"Build a decision app that's YOURS — a personality quiz with scoring, a recommender (what to watch, study, cook, or listen to), a smart advice app, an eligibility checker. Read input, use an if-else-if chain and at least one compound condition, and produce a real result. Pick something you'd actually want to send to a friend."

Make It Yours: Spec Your Logic (15 min)

  • List your INPUTS — which text boxes, numbers, and dropdowns will you read?
  • Write your decision rules as pseudocode / if-then in plain English before touching real code.
  • Identify where a COMPOUND condition is needed — where do two things have to be true at once, or either of two, or the opposite of one?
  • Decide the ORDER of your branches now — most-specific first — so nothing ends up unreachable.

Push students to choose a topic that matters to them — their sport, their playlists, their study habits, their community. A recommender that picks a weekend hike near where they live is more motivating (and easier to test honestly) than a generic one. This is a keepable App Lab project; the link is theirs to share.

Build (50 min)

"Translate your pseudocode into code mode. Wire your inputs, then build the if-else-if chain and drop in your compound condition. Run it after every branch you add — don't wait until the end."

  • Order branches from most-specific to most-general so each one is reachable.
  • Test every path — including the final else.
  • Use == for comparison (never =) and the right operator for each test.
  • console.log the values feeding each condition to trace why a branch ran.

Peer Test (12 min)

  • Swap App Lab links with a partner.
  • Try to find an input that gives a wrong or unreachable result.
  • Give one strength and one specific fix.

Reflection (8 min)

  • Explain your decision logic in plain English — what does your app decide, and how?
  • Where's the Input, the Decision (Processing), and the Output in your app?
  • What branch bug did you hit, and how did you find it?
  • How could an app like this be useful in your own life — at home, at school, or with friends?

AI bridge: When you direct an AI to build an app, you specify its decision RULES. How does understanding conditionals help you state those rules precisely ("if the user picks X and the number is over Y, then Z") AND catch when the AI's logic is wrong — a branch in the wrong order, an unreachable case, an && where you meant ||? Write two sentences.

TEACHER REFERENCE — a small complete recommender in code:

// INPUT: a dropdown + a number var mood = getText("moodDropdown"); // "chill" / "hype" var minutes = getNumber("timeInput"); // free minutes // if-else-if chain, most-specific first, // with one COMPOUND condition if (mood == "hype" && minutes >= 60) { setText("pick", "Go for a run or a workout"); } else if (mood == "hype") { setText("pick", "Play an upbeat song"); } else if (mood == "chill" && minutes >= 30) { setText("pick", "Watch an episode"); } else { setText("pick", "Take a short walk"); }

Classic bug: = vs ==

Writing if (mood = "hype") assigns instead of compares. Fix: use == to ask the question.

Classic bug: unreachable branch from bad ordering

Putting else if (mood == "hype") BEFORE the mood == "hype" && minutes >= 60 branch means the compound branch never runs. Fix: most-specific first.

Classic bug: wrong compound operator

&& where || was meant (or vice versa) changes which inputs match. Fix: read it aloud — "both" means &&, "either" means ||.

Apps vary widely — grade on correct operators, a working if-else-if chain, and a correct compound condition, not on the specific topic.

Additional Notes

Differentiation

  • Support: hand out a skeleton with inputs already wired and one branch done, so students fill in the rest of the chain. Offer a bug-hunt starter that contains an unreachable branch for them to find and fix.
  • Advanced: add nested conditions, validate input before deciding, build a scored quiz with a computed result, or refactor a long chain into cleaner compound conditions. Encourage advanced students to push their own chosen app further — more categories, smarter rules.

For the Non-Technical Teacher

  • The three bugs to know: = vs == (assign vs compare); branch ORDER (specific before general, so nothing is unreachable); and && vs || (both vs either).
  • When a branch runs when it shouldn't, have the student console.log the values being compared — seeing the actual numbers/text usually reveals why.

Connecting the Arc

  • Conditionals are the decision logic of Processing in IOSP: input comes in, a Boolean test decides, output goes out.
  • This is exactly what you specify to an AI builder ("if the user picks X and Y, then Z") and exactly what you debug when its logic is wrong — a wrong branch, an unreachable case, or the wrong compound operator.
