Lesson 1

Event-Driven Code

Most code you've seen runs top to bottom, line by line, then stops. Interactive code works differently. Instead of running once, it registers handlers — chunks of code that sit and wait. Nothing runs until an event fires; then the matching handler wakes up.

This is the callback idea: you define a function now, but the browser calls it back later — only when the event actually happens. You're not running the code; you're handing it over and saying "run this when the time comes."

Event — what happens

The user does something: a click, a keystroke, a swipe. The browser notices and looks for a handler registered for that event.

Handler / Callback — the code you handed over

The function you registered earlier runs now. You defined it in advance; the browser calls it back at the right moment. That's why it's called a callback.

Output — what changes on screen

The handler reads or writes the page — new text, a new color, an updated message. That visible change is what the user experiences.

Event-driven code doesn't run once and quit. It registers handlers, then reacts — over and over — every time an event fires.

Lesson 2

Anatomy of a Handler

Every event handler names three things: what to listen to, which event, and what code to run. Here's the same handler in App Lab and in plain JS:

App Lab style
onEvent("startBtn", "click", function() {
  // this code runs when startBtn is clicked
});
Plain JS (what's in the editor →)
startBtn.addEventListener("click", function() {
  // this code runs when startBtn is clicked
});

Break either one into its three parts:

  • Target — which element is listening: "startBtn" / startBtn.
  • Event type — what to listen for: "click" (could be "input", "keydown", and more).
  • Callback — the function() { ... } that runs when the event fires.

Different words, identical structure. App Lab's onEvent and the browser's addEventListener both say: "on this target, for this event type, run this callback." Read one and you can read the other.

Make It Yours

Make It Yours

Now make the panel yours. You decide what it says, how it looks, and what else it can do:

  • Change Button A: edit the string in heading.textContent so it says something you'd say.
  • Change the theme: edit the two colors in the themeBtn handler to your own light and dark palette.
  • Stretch: add a third button with your own handler — maybe a reset that clears everything, or a counter that ticks up on each click.
Stuck? Example edit

Add a third button with its own handler. First add it to index.html:

<button id="countBtn">Count: 0</button>

Then register its own addEventListener in index.js:

var count = 0;
var countBtn = document.getElementById("countBtn");
countBtn.addEventListener("click", function () {
  count = count + 1;
  countBtn.textContent = "Count: " + count;
});

Three buttons, three handlers — each one reacts to its own event and changes its own piece of the page.

Wrap-Up

The Big Idea

Every interactive app is handlers wired to events. The user does something, the matching callback runs, the page changes. Master that one pattern and you can build — and direct an AI to build — almost any interaction.
