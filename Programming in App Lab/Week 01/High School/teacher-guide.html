Events: Making Things Interactive

Week 1 — Write event handlers in code and build an interactive app screen

At a Glance

Driving Question
How do you write the code that makes an app respond to the user?
Big Idea
Interactive apps are event-driven: you register handlers that run when the user acts. In code, onEvent(id, type, function) wires an element to behavior — input (event) → processing (handler body) → output (property changes).
Schedule
Day 1 Learn (45) · Day 2 Explore (90) · Day 3 Create (90)
Week Deliverable
A hand-coded interactive App Lab screen (multiple events + property changes), shared via link

Learning Objectives

Students will be able to:

  • Build a UI in Design Mode and read the element IDs it generates
  • Write onEvent handlers in code mode for multiple elements and event types
  • Read and set element properties in code (setText, setProperty)
  • Diagnose and fix common bugs from App Lab error messages and mismatched IDs

Day 1 — Learn: Event-Driven Code

onEvent, handlers, and the callback idea

Time Activity
0–7 min Hook — one event vs. dozens of events
7–22 min Mini-lesson — event-driven model, anatomy of onEvent, the handler runs later
22–38 min Write event handlers in code mode
38–42 min Code.org lesson pointer (Lessons 1 & 2)
42–45 min Exit ticket

Hook (7 min)

"In Week 2 of the last unit you hand-coded a click that changed a page. That was one event. Real apps register dozens of them. Today you write event handlers in actual JavaScript and see how an app is really just a set of 'when X happens, run this' rules."

Take one or two quick answers about apps students use daily, then name the pattern: every tap, key press, and swipe is an event that some piece of code is waiting to handle. That is the whole model for the week.

Mini-lesson: The Event-Driven Model (15 min)

"Most of the code you've seen runs top to bottom. Event-driven code is different. You write handlers and then wait — nothing runs until the user does something. Let's name the three ideas that make this work."

  • EVENT-DRIVEN PROGRAMMING — code organized as handlers that run in response to events (a click, a key press), not straight through from top to bottom.
  • EVENT HANDLER / CALLBACK — a function you pass in now so it can be run later, when the event fires. You define the behavior; the app decides when to call it.
  • onEvent — App Lab's way to register a handler: it connects an element to a behavior for a specific kind of event.

"Here's the anatomy of an onEvent call. Read it out loud with me — element id, event type, and the function that runs."

onEvent("startBtn", "click", function() { setText("status", "Started!"); setProperty("status", "text-color", "green"); });
  • "startBtn" — the element id: which element on the screen is being watched.
  • "click" — the event type: what has to happen (here, a click).
  • function() { ... } — the callback: the code that runs when the event fires.

"Notice what the handler does NOT do — it does not run right now. You're handing App Lab a function and saying 'hold onto this and run it WHEN the click happens.' That 'later' is the whole idea of a callback."

Connect to prior learning: this is the same click → handler idea as the Week 2 StackBlitz addEventListener demo. App Lab's onEvent is App Lab's version of the same concept — register a function, run it later.

Write Handlers in Code Mode (16 min)

"Open App Lab. In Design Mode, add a button and a label. Look at the IDs it gives them — you'll type those exact IDs in your code. Now switch to Code mode and TYPE a handler by hand. No dragging blocks today. Wire your button so a click changes the label."

  • Students add elements in Design Mode, then read the auto-generated IDs (case matters — copy them exactly).
  • Students TYPE an onEvent handler in code mode rather than dragging a block.
  • Run the app, click, confirm the label changed. If nothing happens, the id probably doesn't match — check it.
studio.code.org/courses/csp5-virtual/units/1 — Lesson 1 (Intro to App Lab), Lesson 2 (Buttons and Events)

Explain the three arguments of onEvent(id, type, function). Why do we say the handler runs "later"?

Every student typed at least one working onEvent handler in code mode.

Day 2 — Explore: Multiple Events & Properties

Event types, properties, and debugging from errors

Time Activity
0–5 min Review — onEvent anatomy, callback-runs-later
5–25 min Build a multi-element UI + read the IDs
25–55 min Wire multiple events + event types (click, plus keydown or change)
55–78 min Debugging from error messages + console
78–90 min Record vocab + checkpoint

Review (5 min)

"Quick recall: what are the three arguments of onEvent? And when does the callback actually run? Right — you register it now, but it runs later, when the event fires. Today we register lots of them, across different elements and different event types."

Build a Multi-Element UI (20 min)

"In Design Mode, add several elements — buttons, labels, maybe a text input. Give them IDs you'll remember. Then in code mode, reference each one by its id. Here's the pattern: read a property or set one, on whichever element you name."

onEvent("greetBtn", "click", function() { setText("titleLabel", "Welcome!"); setProperty("titleLabel", "text-color", "teal"); setProperty("banner", "background-color", "#2d1b69"); });

Encourage deliberate IDs. When students name elements meaningfully (greetBtn, titleLabel) instead of leaving button1, label2, their code reads like a sentence and bugs get easier to spot.

Multiple Events & Event Types (30 min)

"Wire at least three handlers across different elements. Then push further: events have TYPES. A click is one type. There are others — a key being pressed, or an input's value changing. Let's add a second type of event so your app reacts to more than just clicks."

onEvent("nameInput", "change", function() { var typed = getText("nameInput"); setText("titleLabel", "Hi, " + typed); }); onEvent("titleLabel", "keydown", function(event) { console.log("key pressed: " + event.key); });

Debugging from Error Messages (23 min)

"When something breaks, don't guess — read. App Lab prints an error, usually with a line number. And you can print your own values with console.log to see what the code actually has, versus what you think it has."

onEvent("scoreBtn", "click", function() { console.log("button was clicked"); setText("scoreLabel", "10 points"); });

The #1 bug is an element id in the code not matching the id in Design Mode exactly — IDs are case-sensitive, so scoreBtn and scorebtn are different elements. The second most common bug is forgetting the handler is a function: a missing function() { or an unclosed } / ).

  • Circulate constantly; require at least 3 working handlers per student before the checkpoint.
  • Push students to fix bugs by READING the error and its line number, not by guessing and re-running.
  • Encourage console.log to inspect what a value actually is when behavior surprises them.
  • When a click "does nothing," first suspect an id mismatch — have them compare code to Design Mode letter for letter.

Record Vocabulary (part of 78–90)

  • event-driven programming
  • callback
  • event type
  • setProperty
  • console.log
  • debugging

Every student has 3+ working handlers across multiple elements and has debugged at least one error using the message or the console.

Day 3 — Create: Build an Interactive App Screen

A hand-coded interactive screen — make it yours

Time Activity
0–5 min Launch — the build challenge
5–20 min Plan — spec the elements + events
20–70 min Build in code mode
70–82 min Peer test — swap links
82–90 min Reflection

Launch (5 min)

"Build an interactive screen that's YOURS and coded by hand — a study dashboard, a hype/soundboard, a mini decision helper, a themed reaction app. At least 3 events across multiple elements, with property changes. This is a keepable piece of work with a share link, so make it something you'd actually want to show someone."

Make It Yours: Spec Your Screen (15 min)

"Before you write code, spec it. List your elements with their IDs. Then for each event, write down three things: the id it's on, the event type, and what the handler does. That spec becomes your code — you're basically writing the plan in the same shape as onEvent."

  • Students list every element and the exact id they'll give it in Design Mode.
  • For each planned event: id + event type + what the handler changes (which properties, on which element).
  • Students choose their own topic, audience, and theme — this is the "make it yours" decision point.

The spec is the differentiator between a working screen and a stuck student. If a plan lists an event with no id or no clear action, fix it on paper before any code is typed.

Build in Code Mode (50 min)

  • Keep IDs consistent between Design Mode and code — copy, don't retype from memory.
  • Write one handler, test it, THEN write the next. Don't write all three and debug a pile at once.
  • Use console.log when stuck to see what a value or id actually is.
  • Scope small but working — three solid handlers beat six broken ones.

Peer Test (12 min)

"Swap share links with a partner. Your job is to try to break each other's screen — click things fast, type weird input, do the unexpected. Then report back one thing that worked well and one bug or improvement."

Reflection (8 min)

  • Which part of your code is the input, which is the processing, and which is the output?
  • What bug taught you the most this week, and how did you find it?
  • Why did you choose this theme? Where could a screen like this be useful in your own life — at home, in a club, with friends?
  • Soon you'll direct an AI builder to make apps. How does understanding onEvent handlers help you describe what you want and debug what the AI produces?

TEACHER REFERENCE — a small complete working example: a 2-button toggle app.

Design Mode elements: a label with id lightLabel, a button onBtn, and a button offBtn.

onEvent("onBtn", "click", function() { setText("lightLabel", "Light: ON"); setProperty("lightLabel", "text-color", "green"); }); onEvent("offBtn", "click", function() { setText("lightLabel", "Light: OFF"); setProperty("lightLabel", "text-color", "gray"); });

Bug 1 — id mismatch

Code says onEvent("onbtn", ...) but Design Mode named it onBtn. Clicking does nothing. Fix: match the id exactly, including case.

Bug 2 — missing function wrapper

Code says onEvent("onBtn", "click", setText("lightLabel", "ON")); — this runs setText immediately instead of passing a function. Fix: wrap the body in function() { ... }.

Screens will vary widely by student. Grade on working handlers + correct IDs, not on the specific theme.

Additional Notes

Differentiation

  • Support — provide a code skeleton with element IDs pre-declared and one handler already done, so students fill in the rest. Offer a bug-hunt starter with a planted id-mismatch to practice reading errors.
  • Advanced — add a keydown handler, a timer/interval, or a small state toggle across 4+ elements; refactor repeated code into a shared function. Encourage advanced students to push their self-chosen screen further — a real tool they'd keep using.

For the Non-Technical Teacher

  • You don't need to debug live. Teach students to READ the error line and CHECK the id against Design Mode.
  • The answer key above has the two most common bugs and their fixes — that covers the vast majority of what you'll see.

Connecting the Arc

  • Event handlers are IOSP made real — the event is input, the handler body is processing, the property changes are output.
  • This is also the literacy that lets students DIRECT and DEBUG an AI builder (Lovable) later — they can specify events precisely and spot when generated code is wrong.
