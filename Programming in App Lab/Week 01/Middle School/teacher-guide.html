Events: Making Things Interactive

Week 1 — Design a screen, then make it respond with your first event handlers

At a Glance

Driving Question
How do you make an app DO something when the user clicks?
Big Idea
Apps react to events. You build a screen, then write an event handler that runs when the user acts — input (click) → processing (handler) → output (the screen changes).
Schedule
Day 1 Learn (45 min) · Day 2 Explore (90 min) · Day 3 Create (90 min)
Week Deliverable
A working interactive App Lab screen with at least two events, shared via link

Learning Objectives

Students will be able to:

  • Use App Lab Design Mode to add UI elements (button, label, image) to a screen
  • Explain what an EVENT is and write an event handler (onEvent) that runs on a click
  • Change an element's properties (text, color, image) in response to a click
  • Read a simple error message and fix a basic bug

Day 1 — Learn: What Makes an App Interactive?

Design Mode + your first event

Time Activity
0–8 min Hook — "What happens the instant you tap a button?"
8–22 min Mini-lesson — what App Lab is, Design Mode, what an event is
22–38 min First event handler, together in App Lab
38–42 min App Lab lesson pointer (Code.org Lessons 1 & 2)
42–45 min Exit ticket

Hook (8 min)

"Every app you use is waiting for you to DO something — tap, type, swipe — and then it reacts. Think of an app you love. What happens the instant you tap a button? Today you'll make YOUR screen react to a click."

Take a few quick answers out loud. The point is to surface that apps don't just sit there — they wait, then respond. That "wait, then respond" idea is exactly what an event is.

Mini-lesson: What Is App Lab, and What Is an Event? (14 min)

"We're going to build real apps in a tool called App Lab. Before we touch the code, let's name the five ideas we'll use every single day this week."

  • APP LAB — a place to build real apps with drag-and-drop design plus JavaScript. You get accounts on Code.org.
  • DESIGN MODE — where you place buttons, labels, and images on the screen, like arranging stickers on a page.
  • UI ELEMENT — a thing on the screen: a button, a label (text), or an image.
  • EVENT — something the user does, like a click.
  • EVENT HANDLER — the code that runs when the event happens.

"Here's how this connects to what we already know about IOSP. The click is the INPUT. The event handler is the PROCESSING — it's the code that decides what to do. And changing the screen is the OUTPUT. Input, processing, output — an app is that loop happening over and over."

Keep the click → handler → screen-change idea front and center. Everything this week is a variation on it. If students remember only one thing today, this is it.

Your First Event Handler — Together (16 min)

"Let's build our first reaction together. Everyone open App Lab. Step one: in Design Mode, drag a button onto the screen — it will be named button1. Step two: drag a label onto the screen — it will be named label1. Now switch to Code and let's make the button do something when it's clicked."

onEvent("button1", "click", function() { setText("label1", "You clicked me!"); });

"Read this out loud like a sentence: 'ON the EVENT of button1 being clicked, run this function — set the text of label1 to You clicked me!' Now everyone press Run and click your button. The label should change. That's your first event handler."

For the non-coder teacher: App Lab lets students drag a block that writes this code for them, then shows the text version right next to it. You don't need to memorize syntax — you need students to see "click → something happens." If yours works on the projector, you're ready.

Day 2 — Explore: More Events, More Reactions

Event types, properties, labels — and reading errors

Time Activity
0–5 min Review — event + handler; cold-call the click-handler shape
5–25 min Design Mode practice — add labels, images, style
25–55 min Multiple events + changing properties
55–75 min Debugging basics — reading an error
75–90 min Progress check + record vocab

Review (5 min)

"Quick recall: what's an event? What's an event handler? Someone tell me the shape of a click handler — what comes first, what goes inside?"

Cold-call the click-handler shape: onEvent(id, "click", function() { ... }). Don't worry about perfect syntax out loud — you're checking that they remember "name the element, name the event, then the code that runs."

Design Mode Practice (20 min)

"Let's fill out a screen. In Design Mode, add several elements: a title label at the top, an image in the middle, and two buttons near the bottom. Then set their properties — change the text, the color, and the size. Make it look like something, not just gray boxes."

Properties live in the right-hand panel in Design Mode when an element is selected. Encourage experimenting — this is low-stakes and builds comfort before the code gets busier.

Multiple Events + Changing Properties (30 min)

"Now wire up more than one event. Each button gets its own handler, and each handler can change more than one thing. Watch how this one changes both an image and a label when the cat button is clicked."

onEvent("catBtn", "click", function() { setImage("pet", "cat.png"); setText("caption", "Meow!"); });

"You have three tools for changing the screen: setText changes words, setImage changes a picture, and setProperty can change things like color or size. Give each of your two buttons a different job."

  • Circulate constantly — this is the busiest work of the week
  • Make sure each student has at least TWO different buttons doing TWO different things
  • Encourage changing color, text, and image — not just one kind of change
  • Watch for the common bug of mismatched element IDs: the id in the code must match the id in Design Mode exactly

Debugging Basics: Reading an Error (20 min)

"When something doesn't work, App Lab either shows you an error message or the button just 'does nothing.' Both are normal. Here are the first two things to check every time: Does the element ID in your code match the ID in Design Mode exactly? Is the event type spelled "click"?"

Mismatched IDs are the #1 beginner bug — the code looks right but the name doesn't match. If a handler "does nothing," check the element's ID in Design Mode against the exact text inside the quotes in the code. A capital letter or an extra "1" is enough to break it.

Model debugging out loud once on the projector: intentionally mistype an ID, run it, show that nothing happens, then fix it together. Students learn far more from watching you recover from a bug than from never seeing one.

Record Vocab (part of 75–90 min)

  • event — something the user does (like a click)
  • event handler — the code that runs when the event happens
  • property — a setting on an element (text, color, size, image)
  • setText — changes the words shown on an element
  • setProperty — changes a setting like color or size
  • debugging — finding and fixing what's broken

Every student has a screen with at least two elements responding to two different click events, and has fixed at least one bug.

Day 3 — Create: Build Your Reaction Screen

A screen that reacts — make it yours

Time Activity
0–5 min Launch — build a screen that's YOURS
5–20 min Plan on paper — theme, elements, what each button does
20–70 min Build in App Lab
70–82 min Share & test — get a link, try a partner's
82–90 min Reflection

Launch (5 min)

"Now build a screen that's YOURS — an 'About Me' screen, a reaction or soundboard, a mini pet, a hype-button — anything that reacts when someone clicks. Plan it, build it, share it."

Make It Yours: Plan Your Screen (15 min)

"Before you touch App Lab, plan on paper. Decide three things: your theme, what elements you'll add, and what each button will DO — which property changes when it's clicked. Keep it to 2–4 events. A small screen that fully works beats a big one that's half-broken."

Personalization drives engagement — let students pick a theme they actually care about: their hobby, their team, their pet, their favorite music. The more it's theirs, the harder they'll work to make it run.

Build (50 min)

"App Lab build time. Start in Design Mode, place your elements, then write one handler at a time and test as you go. Get one button working before you add the next."

  • Keep scope small — a few buttons is plenty for Week 1
  • One working event beats five broken ones — celebrate the working one
  • Remind students to test after each change, not at the very end
  • Help with ID mismatches first — it's still the most common bug

Extend Beyond the Classroom: Share & Test (12 min)

"Use App Lab's Share button to get a link to your project. Trade with a partner and try each other's screens. Then take your link home — share it with a friend or a family member outside class, and watch them use the thing YOU built."

The Share link is a keepable artifact — it's a real, usable app the student made and can show anyone. Encourage them to save the link somewhere they'll still have it later in the course.

Reflection (8 min)

  • What does your screen do when someone clicks?
  • Which part of your app is the input, and which part is the output?
  • Why did you choose this theme? What makes it yours?
  • What would you add next if you had more time?

Additional Notes for the Teacher

Differentiation

  • Support: Provide a starter project with one button already wired; a fill-in-the-blank handler; sentence frames for the reflection
  • Advanced: Add a keydown / keyup event, chain multiple property changes in one handler, add sound, or build a two-button toggle

Materials Needed

  • Computers with Code.org App Lab access (student accounts)
  • The student worksheet
  • Projector for the demo

For the Non-Technical Teacher

  • You don't need to write code from scratch — App Lab writes the handler when students drag a block
  • Your job is to keep the "click → reaction" idea front and center, and to help students match element IDs

Connecting the Arc

  • This is IOSP made real — the click is input, the handler is processing, the screen change is output
  • It also sets up the AI-builder capstone: soon students will DIRECT an AI to build apps, and knowing how events work lets them describe and debug what it makes
