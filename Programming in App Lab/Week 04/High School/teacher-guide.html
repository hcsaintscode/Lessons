Functions & a Real App

Week 4 — Functions, decomposition, a full app, and the bridge to AI builders

At a Glance

Driving Question
How do you decompose a real app into functions — and how does that make you effective with AI builders?
Big Idea
Functions package reusable behavior; parameters make them flexible; decomposition breaks a big app into small named functions. Assemble events + variables + conditionals + functions into a complete app. And because you can decompose and read code, you can direct and debug an AI app builder.
Schedule
Day 1 Learn (45) · Day 2 Explore (90) · Day 3 Create (90)
Week Deliverable
A self-chosen app decomposed into functions (using events + variables + conditionals) — shared via link — plus a reflection on directing/debugging AI-generated code

Learning Objectives

Students will be able to:

  • Define and call functions, including functions with parameters
  • Use decomposition to break an app into small, single-purpose functions
  • Assemble events, variables, conditionals, and functions into a complete working app
  • Explain how decomposition and code literacy let you direct and debug an AI app builder

Day 1 — Learn: Functions, Parameters & Decomposition

Package behavior; break big problems into small ones

Time Activity
0–7 min Hook — recap the toolkit
7–24 min Mini-lesson — function definition/call; parameters; decomposition
24–38 min Write a parameterized function + decompose a task into functions
38–42 min App Lab lesson pointer (Code.org Lessons 10–11)
42–45 min Exit ticket

Hook (7 min)

"You have the whole toolkit now — events, variables, conditionals. This week you learn FUNCTIONS with parameters and DECOMPOSITION: breaking a real app into small named pieces. Then you build a complete app and see how this makes you powerful with AI builders too."

On the board, write one long messy list of steps for a game — pick a color, color the buttons, check the click, add points, show the score, switch turns — then draw boxes around groups of related steps and give each box a name. That's decomposition: turning one wall of code into a few named functions you can read at a glance.

Mini-lesson: Functions, Parameters & Decomposition (17 min)

"A function is a named block of code you can run whenever you call it. A parameter is an input you hand the function so it can do its job on different values. Decomposition is the habit of splitting a whole app into small functions that each do exactly one thing."

  • FUNCTION — a named, reusable block of code. Define it once with function doThing() { ... }, then run it any time by calling doThing().
  • PARAMETER — an input a function takes so it can vary its behavior. updateScore(10) passes 10; the same function also handles updateScore(50).
  • RETURN VALUE — a function can hand back a result with return, so a caller can use what it produced (mention briefly; you'll use it more on Day 2).
  • DECOMPOSITION — breaking a program into small, single-purpose functions so it stays readable, testable, and easy to change.
function updateScore(points) { score = score + points; setText("scoreLabel", score); } updateScore(10);

"Now think about a whole game as a set of functions, each with one job: pickTarget() chooses what the player is hunting, checkAnswer() decides right or wrong, updateScore() changes the points. You don't write one giant blob — you write small named pieces and call them."

  • pickTarget() — one job: choose the thing the player is looking for.
  • checkAnswer() — one job: compare the player's choice to the target and decide the outcome.
  • updateScore() — one job: adjust the score and show it.

Tie it back to IOSP and prior weeks: functions organize the Processing step — the logic between Input and Output. Parameters let one function serve many cases instead of copying code. Decomposition is how real programs stay readable: small named functions you (and a teammate, or an AI) can reason about one at a time.

Write & Decompose (14 min)

Students do two quick tasks in App Lab (code mode) or on paper:

  • Write one function that takes a parameter (e.g. greet(name) that sets a text label using the name passed in), then call it twice with different values.
  • Pick a small task — a tip calculator, a name-the-emoji quiz, a step tracker — and name the 3–4 functions you'd decompose it into, one job each. Note which function needs a parameter.

Day 2 — Explore: Build Color Sleuth (Full App)

Decompose and assemble everything

Time Activity
0–5 min Review — parameters + decomposition
5–20 min Color Sleuth architecture — functions, state, conditionals
20–70 min Build — the app, decomposed into functions
70–85 min Test & debug each function
85–90 min Record vocab + checkpoint

Review (5 min)

"Yesterday: a parameter is the input you hand a function, and decomposition is splitting an app into small named functions with one job each. Today we build a whole app that way — Color Sleuth — and you write and organize the functions yourself."

Color Sleuth Architecture (15 min)

"Before we touch code, we plan the app as functions. In Color Sleuth two squares show colors — one is slightly different. Click the different one to score. Ask: what functions do we need, what STATE do we track, and where are the DECISIONS?"

  • makeRandomColor() — produces/returns a color string from random RGB values (one job: make a color).
  • setUpRound() — pick the target, color the buttons for a new round (one job: start a round).
  • checkGuess(buttonId) — takes a parameter; a conditional decides right vs wrong, updates the score, switches the turn (one job: judge a guess).
  • STATE — the score (and whose turn) live in variables declared OUTSIDE the functions so every function can see them.
function makeRandomColor() { var r = randomNumber(0, 255); var g = randomNumber(0, 255); var b = randomNumber(0, 255); return "rgb(" + r + "," + g + "," + b + ")"; } function setUpRound() { var base = makeRandomColor(); setProperty("square1", "background-color", base); setProperty("square2", "background-color", base); // then tweak ONE square so it differs slightly }

setProperty(id, "background-color", color) sets a square's color at runtime; randomNumber(0, 255) gives a random channel value. Building the color string with "rgb(" + r + "," + g + "," + b + ")" is string concatenation — the same skill from Week 3.

Build (50 min)

"App Lab's Lesson 10 gives you the structure. Your job is to write and ORGANIZE the functions — each one doing a single job — and wire them to the buttons so a click calls the right function."

Facilitation targets — hold every student to these:

  • The app is decomposed into at least two named functions, and at least one takes a parameter.
  • Functions are CALLED from event handlers — e.g. onEvent("square1", "click", function() { checkGuess("square1"); });
  • The score is declared OUTSIDE the functions (top of the program) so it persists across clicks.
  • Each function is tested on its own before wiring the next one.
  • Use console.log to see values (the target, the guess, the score) while testing.

A function must be DEFINED before it is called, and its name must be spelled the SAME everywhere. Two classic bugs: a parameter that's declared but never passed in (so it's undefined inside), and a value passed in but never used (so the function ignores it). When behavior looks wrong, console.log the parameter at the top of the function to see what actually arrived.

Record Vocab (5 min)

  • function · parameter · return value · decomposition · setProperty · Math.random (or randomNumber)

Every student has a working Color-Sleuth-style app decomposed into 2+ functions (one parameterized), assembling events + a variable + a conditional.

Day 3 — Create: Capstone App + the AI Bridge

Ship your own app; then connect to directing/debugging AI

Time Activity
0–5 min Launch the capstone
5–20 min Spec + decompose your app
20–62 min Build — one function at a time
62–75 min Peer test + showcase
75–90 min The AI bridge + reflection

Launch (5 min)

"Your capstone: build a real app of YOUR choice — a scored game, a tool, a tracker, a recommender — DECOMPOSED into functions, using events + variables + conditionals. Ship it."

Make It Yours: Spec & Decompose (15 min)

"Pick something you actually care about — a scorekeeper for a game you play, a tool for your team or club, a tracker for a habit, a recommender for friends. First DESCRIBE it in a sentence, then DECOMPOSE it: list the functions you'll write."

  • Describe the app in one sentence: what does it do, and for whom?
  • List the FUNCTIONS you'll write — one job each — and note which ones need a parameter.
  • Identify the STATE (what variables must persist) and the DECISIONS (where a conditional chooses a path).

Encourage students to choose an app that fits their own world — a hobby, their school, family, or community — and to build something they'd actually keep or use. A durable App Lab link they can share is worth more than a generic worksheet task.

Build (42 min)

Code-mode build. Facilitation targets:

  • Write ONE function, test it, then move to the next — don't write the whole app before running anything.
  • Keep each function single-purpose; if a function does two things, split it.
  • Use parameters where they remove duplication (one function instead of near-identical copies).
  • Use console.log to watch values while testing each function.
  • Working over fancy — a small app that runs beats a big one that doesn't.

Peer Test + Showcase (13 min)

  • Swap App Lab links with a partner.
  • Find one bug in a partner's logic or a function (a wrong branch, an unpassed parameter, a name typo).
  • Demo your app and walk through your functions — name each one and what its single job is.

The AI Bridge (15 min)

"Next you'll build apps with an AI tool (Lovable) that generates real code from a description. Two ways this unit makes you powerful: (1) you can DECOMPOSE and SPECIFY exactly what you want — 'it needs a function that does X, state that tracks Y, and this decision rule' — so the AI builds the right thing; (2) you can READ, TEST, and DEBUG what it generates — spotting a wrong branch or a broken function and fixing it or directing a precise change. You audit the AI."

  • How would you specify your capstone app to an AI builder using the vocabulary of functions, state, and conditionals?
  • An AI builds an app but one feature silently fails — how do you find and fix it now?
  • What's the difference between accepting AI output and directing it?

Reflection

Describe your app's functions, state, and decisions. Where are the Input, Processing, and Output? What bug did you find via decomposition or console.log? Then the AI bridge: How does understanding functions and decomposition change how you'll DIRECT and DEBUG an AI app builder like Lovable? Where could an app like yours be useful in your own life — at home, in your community, or with friends?

TEACHER REFERENCE

var score = 0; var target = ""; function makeTarget() { var choices = ["red", "green", "blue"]; target = choices[randomNumber(0, 2)]; setProperty("square1", "background-color", target); } function updateScore(points) { score = score + points; setText("scoreLabel", score); } function checkGuess(id) { if (getText(id) == target) { updateScore(10); } else { updateScore(-5); } makeTarget(); } onEvent("guessBtn", "click", function() { checkGuess("guessBtn"); }); makeTarget();

Classic bug: call-before-define / name typo

Calling makeTarget() before it's defined, or writing checkGuess in one place and checkguess in another. Fix: define functions first; spell names identically everywhere.

Classic bug: parameter passed but unused (or used but not passed)

updateScore() called with no argument means points is undefined; or a function reads id but the handler never passes one. Fix: pass the value in and use the same parameter name inside — console.log it to confirm.

Classic bug: score scope

Declaring var score = 0; INSIDE a function resets it every call. Fix: declare state OUTSIDE the functions so it persists.

Apps vary widely — grade on real decomposition, at least one parameterized function, and correct integration of events + a variable + a conditional, not on the specific topic.

Additional Notes

Differentiation

  • Support: provide a function skeleton — the function names with empty bodies — for students to fill in. Let them decompose a scoped-down Color Sleuth (fewer rounds, one square to click) rather than an open-ended app.
  • Advanced: write functions that return values, parameterize multiple functions, add a two-player mode with turn-switching, or refactor duplicated code into one shared function. Encourage advanced students to push their own chosen app further.

For the Non-Technical Teacher

  • The bugs to know: define-before-call and consistent names, and parameters must actually be PASSED (not just declared). When a function misbehaves, have the student console.log its parameter to see what arrived.
  • Celebrate the milestone: students can now BUILD and REASON ABOUT a whole app — events, state, decisions, and named functions working together.

Connecting the Arc — the Lovable bridge

  • This unit hands off to the Problem Solving & Computing capstone, where students build with lovable.dev.
  • Decomposition + code literacy = the ability to SPECIFY precisely ("a function that does X, state that tracks Y, this decision rule") and to DEBUG AI-generated apps — not just accept whatever the AI produces.
