Lesson 1

Variables = Named Memory

A variable is a named slot in memory that the program can read and rewrite. You give it a name, put a value in it, and later the program can look it up or replace it. That's how an app remembers anything at all.

The trickiest part for new coders: the = sign is assignment, not equality. score = 5 doesn't claim "score equals five" — it commands "put 5 into the slot named score." So read x = x + 1 right-to-left: first work out x + 1 using the current value, then store that result back into x.

Declare — create the slot

var score = 0; makes a named slot called score and puts 0 in it. You declare a variable once.

Assign — put a value in

= stores the value on the right into the slot on the left. score = 5 overwrites whatever was there before.

Update — rewrite using the old value

score = score + 1: read the current score, add one, store the result back. Read it right-to-left and it makes sense.

A variable is a named slot the program reads and rewrites. = means "store this here," so x = x + 1 reads right-to-left: compute, then save back.

Lesson 2

Scope & State

Where you declare a variable decides whether it persists. This is called scope, and it's the difference between an app that remembers and one that keeps forgetting.

  • Declare it outside a handler and it survives across events — every click reads and updates the same slot.
  • Declare it inside a handler and it's recreated from scratch every call — so it resets to zero every single time. This is the #1 state bug for beginners.

Put it together: variables + events = state. Events are when things change; variables are what the app is holding onto. State is the set of values your app currently remembers — the score right now, whose turn it is, what's typed in the box.

The scoreboard on the right keeps two scores as variables declared ONCE outside the handlers. Because they live in the outer scope, each click updates a slot that's still there next time.

Make It Yours

Make It Yours

Now make the scoreboard yours. Pick a game or contest you actually play — you vs. a friend, two teams you follow, siblings racing chores — and reshape the board around it:

  • Rename the players/labels: change the text in index.html so it says your two players' names.
  • Make one button worth 2 points: change that handler's update to + 2 instead of + 1.
  • Stretch: add a third variable — a "leader" message that shows who's ahead. A simple compare works, or track a running total. This is state you invented.
Stuck? Example edit

Add a third variable that reports who's leading. First add a place to show it in index.html:

<p id="leader"></p>

Then in index.js, grab that element once and write a little function that compares the two scores. Call it after every update:

var leaderEl = document.getElementById("leader");

function showLeader() {
  if (p1 > p2)      leaderEl.textContent = "Player 1 leads!";
  else if (p2 > p1) leaderEl.textContent = "Player 2 leads!";
  else              leaderEl.textContent = "Tied!";
}

// call showLeader(); at the end of each button handler

Three variables now: two scores plus a derived "leader" that depends on them. That's exactly how real apps build richer state out of simpler pieces.

Reflect

State & Directing AI

When you direct an AI to build an app, you won't just describe what happens on a click — you'll tell it what state to keep. Knowing how variables and scope work means you can name the state precisely, and you can catch it when the AI wires that state up wrong.

Wrap-Up

The Big Idea

State is the values your app remembers and changes. Manage it well and your app behaves; manage it badly and you get the classic bugs — a score that won't stick, a counter that resets every click. It's also exactly what you'll direct an AI to keep when you describe an app you want built.
