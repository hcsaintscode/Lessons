Variables & State: Apps That Remember

Week 2 — Store, update, and reason about state in code

At a Glance

Driving Question
How does code store and change the values that make an app work?
Big Idea
Variables hold state — values the program reads and updates over time. Combined with event handlers, variables let an app track and respond to what's happened (a score, a streak, a total). Scope matters: where you declare a variable decides whether it persists.
Schedule
Day 1 Learn (45) · Day 2 Explore (90) · Day 3 Create (90)
Week Deliverable
A code-mode app that manages at least two variables updated by events (e.g., a scoreboard), shared via link

Learning Objectives

Students will be able to:

  • Declare, assign, and update variables in code; explain the assignment x = x + 1
  • Explain the labeled-box / memory mental model and why declaration SCOPE matters (inside vs outside a handler)
  • Combine multiple variables with event handlers to model app state (a scoreboard)
  • Debug state bugs using console.log to inspect values over time

Day 1 — Learn: Variables & the Mental Model

Storage, assignment, and scope

Time Activity
0–7 min Hook — from reacting to remembering
7–24 min Mini-lesson — variable as named memory; assignment vs equality; declaration & scope
24–38 min Declare / update a variable in code + display it
38–42 min App Lab lesson pointer (Code.org Lessons 3–5)
42–45 min Exit ticket

Hook (7 min)

"Last week your handlers reacted to clicks but forgot everything instantly. Today they get MEMORY. A variable is a named slot in memory the program can read and rewrite — that's what turns clicks into a score."

Push for precision this year. Ask: where does that number actually live between clicks? Steer them toward the answer "in a variable that the program keeps around" — that persistence is the whole point of state, and it's exactly what scope will decide.

Mini-lesson: Named Memory, Assignment & Scope (17 min)

"There are five moves with a variable. The first four you may have seen. The fifth — scope — is what separates an app that keeps score from one that resets to 1 forever."

  • VARIABLE — a named place in memory that stores a value.
  • DECLARE — create the name: var score;
  • ASSIGN — put a value in: score = 0;
  • UPDATE — recompute and store: score = score + 1;
  • SCOPE — where a variable "lives." Declared OUTSIDE a handler it persists across every click; declared INSIDE, it's recreated from scratch each call.

"Two things trip people up. First: the = sign is ASSIGNMENT, not equality — it does not claim two things are equal, it stores the right side into the left. Second: read score = score + 1 right-to-left. Evaluate the right side using the current value, THEN store the result back in score."

// declared OUTSIDE the handler — it persists var score = 0; setText("scoreLabel", score); onEvent("plusButton", "click", function() { // recompute using the current value, store it back score = score + 1; setText("scoreLabel", score); });

Connect to IOSP: a variable is the STORAGE of IOSP, expressed in code. Input comes from events, Output is what you display, Process is the update, and the variable is where state is kept between them.

Declare, Update & Display — Together (14 min)

"Open App Lab in CODE mode. In Design, add a label with id scoreLabel and a button with id plusButton. In Code, declare score at the TOP of the file — outside any handler — assign it 0, display it, then update it inside the click. Watch it climb and stay climbed."

Do the scope experiment live: move var score = 0; inside the handler and click a few times. It sticks at 1. Move it back out. Seeing the difference beats explaining it.

App Lab Lesson Pointer (4 min)

This week builds on Code.org csp5-virtual Unit 1: Lesson 3 (Multi-screen Apps + console.log debugging), Lesson 4 (Variables and the mental model), and Lesson 5 (Clicker Game).

Exit Ticket (3 min)

Why is = not the same as equals in math? Why does declaring a variable INSIDE a click handler break a running score?

Day 2 — Explore: State With Multiple Variables + Debugging

A scoreboard, and inspecting state with console.log

Time Activity
0–5 min Review — assignment + scope
5–20 min Build the Clicker in code
20–50 min Extend to multiple variables (a scoreboard)
50–75 min console.log debugging of state
75–90 min Vocab + checkpoint

Review (5 min)

"Two things from yesterday: = stores the right side into the left, and a variable declared outside a handler persists while one declared inside resets. Hold both — today we run several variables at once and they only stay in sync if the scope is right."

Clicker in Code (5–20 min)

"Start from the base clicker — one variable, one button, one display. Get it working end to end before adding anything. This is your known-good starting point."

var score = 0; setText("scoreLabel", score); onEvent("plusButton", "click", function() { score = score + 1; setText("scoreLabel", score); });

Multiple Variables (20–50 min)

"Now extend it: track TWO values instead of one. Two options — the current score plus a high score, or two players who each have their own score. Each variable gets its own declaration outside the handlers, and each gets its own display. Every button updates exactly one variable."

// two players, each with their own state var scoreA = 0; var scoreB = 0; setText("scoreALabel", scoreA); setText("scoreBLabel", scoreB); onEvent("buttonA", "click", function() { scoreA = scoreA + 1; setText("scoreALabel", scoreA); }); onEvent("buttonB", "click", function() { scoreB = scoreB + 1; setText("scoreBLabel", scoreB); });

If a group is ready for a high score, high = Math.max(high, score); is a clean one-liner that keeps the largest value seen. Comparisons with if arrive next week, so keep it to this — mostly the goal is two variables that each track and display correctly.

console.log Debugging (50–75 min)

"Add console.log lines to print your variables as they change, then watch the console while you click. This is how professionals find state bugs — you SEE the value at each step instead of guessing what it must be."

onEvent("buttonA", "click", function() { scoreA = scoreA + 1; console.log("scoreA is now " + scoreA); setText("scoreALabel", scoreA); });

The two classic state bugs: the SCOPE bug — declaring a variable inside the handler, so it resets every click — and the WRONG-VARIABLE bug — a typo or copy-paste that updates or displays the wrong name (button B secretly bumping scoreA). Both are invisible in the code at a glance. Inspect with console.log rather than guessing.

  • Require at least two variables, each updated by an event and each displayed.
  • Students add console.log to verify each variable changes as expected.
  • Watch for the scope bug (declared inside a handler) and the wrong-variable bug (updating/displaying the wrong name).

Record Vocab (75–90 min)

  • variable — a named place in memory that stores a value
  • assignment — storing the right side into the variable on the left
  • scope — where a variable lives and how long it persists
  • state — the values an app is currently holding
  • expression — code that computes a value (e.g., score + 1)
  • console.log — prints a value so you can inspect state over time

Every student has an app tracking 2+ variables via events, both displayed, and debugged with console.log.

Day 3 — Create: Build a Stateful App

A scoreboard/tracker of your choice — make it yours

Time Activity
0–5 min Launch the build
5–20 min Spec the state
20–70 min Build in code mode
70–82 min Peer test
82–90 min Reflection + AI bridge

Launch (5 min)

"Build an app that MANAGES STATE — a two-player scoreboard, a habit streak tracker, a budget/points app, a game score. At least two variables, updated by events, displayed live. Pick something you'd actually use — for a team you're on, a habit you're building, a game you play."

Make It Yours: Spec Your State (5–20 min)

"Before you touch code, write the spec. This is the part that makes the app yours, and it's the part that makes it debuggable."

  • List your variables — for each: its name, what it stores, and its starting value.
  • For each button: which variable(s) it updates, and how (what expression).

Encourage students to choose a tracker that connects to their own life — a score for their team, a streak for a habit, points for something they care about. A spec they wrote for their own app is far easier to debug than a generic one.

Build (20–70 min)

"Code mode. Work from your spec: declare every variable at the top, wire each button to update the right one, display all of them. Print with console.log as you go so you can see state changing."

  • Declare variables at the right scope — outside the handlers.
  • Update the RIGHT variable in each button (match it to your spec).
  • Test with console.log before assuming it works.
  • Keep it working over fancy — a solid two-variable app beats a broken elaborate one.

Peer Test (70–82 min)

"Swap links with a partner. Try to find a state bug — a value that goes wrong, resets, or updates the wrong number. Give one strength and one specific fix."

Reflection + AI Bridge (82–90 min)

  1. Name your variables and what state each one holds.
  2. In your app, where is Storage (the state), where are the events, and where is the output?
  3. What state bug did you hit, and how did console.log help you find it?

AI bridge: "When you direct an AI to build an app, you'll need to specify what STATE it should keep. How does understanding variables help you describe that clearly — and catch when the AI mismanages state (loses a value, resets it, or updates the wrong one)?"

Have students save the App Lab share link somewhere they'll keep it. This is a real, usable app they built — a scoreboard or tracker they can actually use and add to later.

TEACHER REFERENCE

A small complete two-variable scoreboard — both declared outside, two buttons updating each, both displayed:

var scoreA = 0; var scoreB = 0; setText("scoreALabel", scoreA); setText("scoreBLabel", scoreB); onEvent("buttonA", "click", function() { scoreA = scoreA + 1; setText("scoreALabel", scoreA); }); onEvent("buttonB", "click", function() { scoreB = scoreB + 1; setText("scoreBLabel", scoreB); });

Bug 1 — Scope (declared inside the handler)

If var scoreA = 0; is placed INSIDE the click handler, it resets to 0 every click, so the display sticks at 1. Fix: declare it once at the top, outside all handlers.

Bug 2 — Wrong variable name

Button B updates or displays scoreA instead of scoreB (a typo or copy-paste). One score climbs, the other never moves. Fix: match each button to its own variable; confirm with console.log.

Apps vary — grade on correct scope, correct updates, and consistent display, not on the specific tracker chosen.

Additional Notes

Differentiation

  • Support — hand out a skeleton with variables declared and the display wired, so the student writes only the update. Offer a scope bug-hunt starter (a version with the scope bug planted) to fix.
  • Advanced — add a high score with Math.max, a derived value (e.g., the difference between two scores), or persist a value with localStorage as a preview of real storage.

For the Non-Technical Teacher

  • The two bugs to know: declaring a variable INSIDE the handler (it resets every click), and updating or displaying the WRONG variable name (a value that never moves or moves when it shouldn't).
  • console.log is how you SEE state — teach students to print a value before guessing what it is. The console shows the truth.

Connecting the Arc

  • Variables are IOSP's Storage in code — the app's memory that holds state between events.
  • This is exactly what you'll later tell an AI builder to manage. Knowing how state works lets you specify it clearly and debug when generated code loses or corrupts it.
