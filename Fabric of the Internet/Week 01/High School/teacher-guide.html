Building a Reliable Network

Week 1 — Topologies, addressing, routing, redundancy, packets, and the TCP/UDP tradeoff

At a Glance

Driving Question
What design principles let an unreliable, decentralized network deliver data correctly and at scale?
Big Idea
The Internet works because of deliberate design choices: shared routing instead of full connection, unique addressing, redundancy for resilience, packets for efficiency, and protocols (TCP/UDP) that trade reliability against speed.
Schedule
Day 1 Learn (45 min) · Day 2 Explore (90 min) · Day 3 Create (90 min)
Week Deliverable
A network design (for a context the student chooses) that is addressed, routed, and made redundant — with a written tradeoff rationale

Learning Objectives

Students will be able to:

  • Explain why the Internet uses shared routing rather than a fully-connected topology, and why that scales
  • Read and reason about IP addresses and a routing table to trace data paths
  • Explain how redundancy provides fault tolerance, and identify single points of failure
  • Describe how packets enable efficient transfer, and justify TCP vs UDP for a given use case

Day 1 — Learn: Why a Network Is Built This Way

Decentralization, topology, and scale

Time Activity
0–7 min Hook — "Why would wiring everyone to everyone be a catastrophe?"
7–22 min Mini-lesson — the Internet as a decentralized network of networks; topology; scaling
22–38 min Scaling activity — fully-connected vs shared routing math
38–42 min Optional enrichment (Internet Simulator) + share-out
42–45 min Exit ticket

Hook (7 min)

"The Internet has no central control computer. If you wanted to connect a billion devices, your first instinct might be to wire everyone to everyone. Why would that be a catastrophe?"

Let students argue it out for two minutes before formalizing. Push them past "too many wires" toward the real problems: cost, physical impossibility, and what happens every time one new device joins. You'll quantify this in the scaling activity.

Mini-lesson: A Decentralized Network of Networks (15 min)

"There is no master computer running the Internet. It's a network built out of many smaller networks that agree to pass data along for each other. That decentralization is a feature, not a flaw — it's what lets the system survive damage and keep growing. Let's define the pieces precisely."

  • INTERNET — a decentralized global network of networks with no single point of control; no one machine has to be working for the whole system to function.
  • ROUTER — a device that forwards packets between networks, choosing a next hop toward the destination.
  • TOPOLOGY — the arrangement of how devices are connected to one another.
  • SCALABILITY — how well a design keeps working as it grows to many more devices.

"Here's the key design choice. A fully-connected network needs a direct link between every pair of devices — that's n(n−1)/2 links, and it explodes as n grows. Instead the Internet uses SHARED ROUTES through routers. Adding one device adds about one link, not one link to every other device. That single decision is why a global network is even possible."

Non-CS teachers: you do not need to be a network engineer for this. The whole lesson rests on one comparison — "a link between every pair" vs "share the roads." Keep pulling students back to that contrast.

Scaling Activity (16 min)

The Cost of Connecting Everyone

"On your worksheet, compute the number of links a fully-connected network needs using n(n−1)/2 for n = 5, 10, 50, and 1000 devices. Then describe in one sentence what happens to the wiring as the network grows."

  • Have students compute each value by hand before revealing the pattern — the jump from 50 to 1000 devices is the "aha."
  • Ask: "If adding the 1000th device to a fully-connected network means adding 999 new links, how many links does adding a device to a shared-routing network cost?" (About one.)

This is the CS Principles "Building a Network" insight: full connection grows like O(n²), while shared routing grows roughly linearly. That difference is the reason the Internet can scale to billions of devices.

Optional Enrichment + Share-Out (4 min)

If your class has Code.org access, the Internet Simulator lets students build a small network and watch shared routing in action. It's entirely optional — no login is required for this unit, and every activity works unplugged.

Code.org · CS Principles (Internet Simulator, optional)

"Why doesn't the Internet connect every device directly to every other device? What does it do instead?"

Every student can explain why shared routing scales and full connection doesn't.

Day 2 — Explore: Addressing & Routing

How data finds its way — and survives failure

Time Activity
0–5 min Review — decentralization + why routing scales
5–15 min Mini-lesson — IP addressing & next hop
15–45 min Routing-table lab — trace paths from source to destination
45–70 min Redundancy analysis — find and fix single points of failure
70–85 min Packets + unplugged packet activity
85–90 min Record vocabulary

Review (5 min)

"Yesterday we established two things: the Internet is decentralized, and it uses shared routing so it can scale. Today we answer the obvious follow-up — if data doesn't have a direct wire to its destination, how does it actually find its way there? And what happens when a piece of the network fails?"

Mini-lesson: IP Addressing (10 min)

"For a router to forward data, it has to know where the data is going. Every device on a network has an address — an IP address — and each router keeps a table telling it where to send data next based on that address."

  • IP ADDRESS — a unique numeric identifier for a device on a network (for example, 192.168.2.2).
  • NEXT HOP — the next router a packet is forwarded to on its way toward the destination.

"A router doesn't know the whole path to the destination. It only decides one thing: given this destination IP address, what is my next hop? It looks up the destination in its routing table, forwards the packet to the next router, and that router does the same thing again — until the data arrives."

Routing-Table Lab (30 min)

"Use the routing table and network diagram on your worksheet. For each scenario, trace how data gets from the source to the destination and list, in order, every router the data passes through."

  • Students look up the destination IP in each router's table, follow the next hop, and repeat until they reach the host.
  • Have them write the hop list as an ordered sequence (e.g., A → B → C → host) so paths are easy to compare.

Watch for scenarios where TWO different paths could reach the same destination. Flag those out loud — they set up the redundancy work in the next block.

Redundancy Analysis (25 min)

  • REDUNDANCY — multiple paths through the network so it can tolerate a failure without disconnecting.
  • SINGLE POINT OF FAILURE — a component whose failure disconnects part of the network from the rest.

"On the diagram, find a single point of failure — a router or link that, if it went down, would cut some devices off completely. Add one new link that removes it, then trace the backup path the data would take instead. Redundancy isn't an accident; it's a design decision."

The test for a single point of failure: cover one component with your finger. If any device can no longer reach any other device, that component is a single point of failure.

Packets + Unplugged Activity (15 min)

  • PACKET — a small, numbered unit of data; a large message is split into many packets that travel independently.

"Let's run a quick packet activity. Split a short message into numbered packets on separate cards. Shuffle them so they arrive out of order, and set one aside as 'lost.' The receiving group reassembles the message by number and requests the missing packet by its number."

Students assume packets travel together and arrive in order. Emphasize the opposite: packets may take different routes and arrive out of order, and some may be lost entirely. Numbering plus acknowledgment is what makes reliable delivery possible on top of an unreliable network.

Record Vocabulary (5 min)

  • IP address
  • Next hop
  • Redundancy
  • Single point of failure
  • Packet

Every student traced a routing path, found and fixed a single point of failure, and reassembled a packetized message.

Day 3 — Create: Protocols & a Reliable Design

TCP vs UDP, and engineering a resilient network

Time Activity
0–5 min Recap — addressing, routing, redundancy, packets
5–25 min Mini-lesson — TCP vs UDP tradeoff + discussion
25–55 min Design challenge — a reliable network for a context YOU choose
55–70 min Tradeoff write-up
70–85 min Peer review — try to break your partner's network
85–90 min Personal-relevance reflection

Recap (5 min)

"You can now address devices, route data across a network, build in redundancy, and split data into packets. One question is left: once packets arrive, do we insist that every single one gets there in order — or do we prioritize speed and accept some loss? That's a protocol decision."

Mini-lesson: TCP vs UDP (20 min)

  • TCP — guarantees that all packets arrive and are put back in order; used for the web, email, and file transfer. The guarantee costs some speed (it waits for acknowledgments and resends lost packets).
  • UDP — fast, with no guarantee of delivery or ordering; used for live video, voice, and gaming. It trades reliability for speed — a dropped packet is better than a delayed one.

"There's no 'better' protocol — there's a tradeoff. TCP asks: did every packet arrive? UDP asks: is the data still useful if it shows up a half-second late? Answer that second question and you usually know which protocol to pick."

  1. Which protocol would you use for a live esports stream? Why?
  2. Which protocol would you use for downloading a game update? Why?
  3. What goes wrong if a video call used TCP?
  4. What goes wrong if a bank transfer used UDP?

Make It Yours: Design a Reliable Network (30 min)

"Now you're the network engineer. Design a network for a context YOU choose — your home, a school computer lab, a small business you'd want to start, an esports team spread across cities, anything you actually care about. Requirements: assign IP addresses to the devices, show your routers and how data is routed, build in REDUNDANCY so there's no single point of failure, and label where you'd use TCP versus UDP."

Let students pick a context that means something to them — the design decisions are the same, but the motivation is personal. As they work, pressure-test every design with one question: "What single failure breaks this?" If they can answer it, they haven't finished adding redundancy.

Tradeoff Write-Up (15 min)

"Write a short rationale for your design. What did you optimize for — speed, reliability, or cost? What did you trade away to get it? Name at least one place you chose TCP and one place you chose UDP, and explain why each fits."

Peer Review (15 min)

"Swap designs with a partner. Your job is to try to BREAK their network — hunt for a single point of failure they missed. Then give them one genuine strength and one specific improvement."

Personal-Relevance Reflection (5 min)

"Now that you understand how the Internet is engineered for reliability, what's one system in your own life — your home WiFi, your phone's connection, a game you play — that you understand differently now, and what would you change about it?"

Scaling math — links = n(n−1)/2

n = 5 → 10 links · n = 10 → 45 · n = 50 → 1,225 · n = 100 → 4,950 · n = 1,000 → 499,500. The jump from 50 to 1,000 devices (1,225 → 499,500) is the point: full connection grows like n², so shared routing is the only way to scale.

Worked routing trace (example table)

Given: Router A next hop for 192.168.2.x → Router C; Router C next hop for 192.168.2.2 → host directly. Data addressed to 192.168.2.2 starting at A: A forwards to C, C delivers to the host. Hop list: A → C → host (192.168.2.2).

Designs will vary by chosen context — that's expected. Grade on whether redundancy removes ALL single points of failure (use the finger-cover test) and whether every TCP/UDP label is justified by its use case (order/completeness vs speed).

Every student produced an addressed, routed, redundant network design with a justified tradeoff rationale and a personal reflection.

Additional Notes for the Teacher

Differentiation

  • Support: Provide a partial routing table and a diagram with one obvious single point of failure to fix; offer sentence frames for the tradeoff rationale ("I optimized for ___ because ___; I gave up ___.")
  • Advanced: Introduce subnetting basics; have students compute paths on a larger topology; research how real ISPs peer with one another; or model and compare latency across alternate paths and let them push their own chosen design further

Materials Needed

  • The student worksheet
  • Graph paper or a diagramming tool
  • Index cards for the unplugged packet activity
  • Projector
  • Optional: computers for the Internet Simulator

Extend Beyond the Classroom

  • Have students diagram their ACTUAL home network and identify its single point of failure
  • Run a real traceroute (macOS/Linux) or tracert (Windows) to a favorite site and count the hops it takes to get there
