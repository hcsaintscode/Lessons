Lesson 1

Why Shared Routing?

The Internet has no central boss. It's decentralized — millions of independent machines cooperating with no single computer in charge. That design is what makes it hard to take down. But it raises a real engineering problem: how do you connect everyone?

The naive idea — wire everyone to everyone

Give every machine a direct cable to every other machine. With 4 computers that's manageable. With millions, it's impossible.

The scaling problem — it grows like n²

Connecting n machines directly needs n(n-1)/2 links. 10 machines → 45 links. 1,000 → ~500,000. This growth is O(n²): double the machines and you nearly quadruple the wiring. It never scales.

The fix — routers + shared routes

Instead, machines connect to routers, and routers pass data along shared paths. Each machine only needs a few links, and data hops router-to-router to reach anyone. That scales to billions.

Lesson 2

Addressing, Redundancy & Packets

Routing only works if data knows where it's going. Every device has an IP address — its identity on the network. A router reads the destination address and forwards the data to the next hop that gets it closer, like a series of road signs pointing the way.

Redundancy — more than one path

If there's only one route and it breaks, everything downstream is cut off — a single point of failure. The Internet builds in redundancy: multiple paths, so if one router or cable fails, data reroutes around the damage.

Packets — data, chopped up and numbered

Big messages are split into small packets, each stamped with a sequence number. Packets travel independently, may take different routes, and often arrive out of order. The receiving computer reassembles them by sequence number — and can tell if one never showed up.

Run It

Run the Packet Reassembler

The editor on the right is running a Packet Reassembler. An array of packets — each with a seq (sequence number) and a piece of text — arrives shuffled, and one packet is missing (it was lost in transit).

The code does three things: it sorts the packets by sequence number to restore the original order, detects the gap where a sequence number is missing, and writes the reassembled message plus any missing packet numbers to the screen.

Make It Yours

Make It Yours

Now change the code on the right. Start small — each of these is a real edit, and you get to decide what the message says and how the network misbehaves:

  • Change the message: rewrite the text of each packet so it spells out your own sentence.
  • Shuffle differently: reorder the packets in the received array so they arrive in a new jumbled order.
  • Drop a different packet: remove a different seq and confirm the gap detector finds that one.
  • Stretch: drop two packets and make sure the output lists every missing sequence number, not just one.
Stuck? Example edit

Write your own message by editing the text values in the received array in index.js:

var received = [
  { seq: 3, text: "own " },
  { seq: 1, text: "This " },
  { seq: 4, text: "message!" },
  { seq: 2, text: "is my " },
  // seq numbers you leave out become "missing"
];

The gap detector already handles more than one missing packet — it collects every gap into the missing array:

for (var i = 1; i <= maxSeq; i++) {
  if (present.indexOf(i) === -1) missing.push(i);
}

Leave out both seq: 2 and seq: 4, run it, and the output should report MISSING packet(s): 2, 4.

Reflect

Reliability in Your Life

Packet loss and reliability tradeoffs aren't abstract — you feel them all the time. A video call freezes and skips ahead; a game "rubber-bands" your character back; a download pauses and then resumes right where it left off. Those are all decisions about reliability vs. speed.

TCP guarantees delivery and order (it resends lost packets) — great for downloads and messages, but slower. UDP just fires packets off and doesn't wait for resends — great for live video and games where being fast matters more than being perfect.

Wrap-Up

The Big Idea

Reliability is engineered. It doesn't happen by accident — it's built from addressing, redundancy, numbered packets, and protocols that deliberately trade speed for certainty. The unreliable network underneath becomes reliable because smart rules sit on top of it. You just built one of those rules yourself.
